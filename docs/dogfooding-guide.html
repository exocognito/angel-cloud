Dogfood the first Angel

Two things stop you before step 6 — a seven-day npm age gate and a bindings key the published docs still spell staging — and both have one-line fixes below. Everything past them has never been walked by anyone, which is the whole point of the run.

Standing guide first; the dated session sheet at the foot carries everything that will be wrong next month. Jump to today's coordinates and blockers →

Rules of the run

The definition of done in ROADMAP.md: starting from an empty directory with no repo clone, you and an agent create, publish, promote, and query a new Angel over MCP; every friction found becomes an issue.

  • Empty directory, no clone. If you or the agent reaches for git clone exocognito/angel-cloud or runs bun run angel inside the product repo, the run is void — the clone hides the friction the run exists to find.
  • Give the agent the docs URL and nothing else. No context from this page, no repo paths. What the agent cannot work out from llms.txt is the finding.
  • Both management credentials are environment variables only. Never in source, angel.json, a log, a command transcript, or an Angel artifact — including anything you paste into a chat.
  • The Angel keys print exactly once. On the first ensure, publish prints the preview and production keys and never shows them again. Have somewhere to put them before you run it.

Three secrets, three rules

Secret Held by May appear in Never appears in
ANGEL_MANAGEMENT_TOKEN You Shell environment Any file, any transcript
ANGEL_ACCESS_TOKEN You Shell environment Any file, any transcript
Angel key ak_… The agent Your secret store; the agent's MCP config The repo; a second environment

The Google credential is not on this list because you never hold it. It goes into Broker custody write-only and no API reads it back.

The required path

Eight steps. The right-hand line is what proves the step landed — if you cannot see it, the step did not happen, whatever the exit code said.

  1. 1

    Install the CLI

    pnpm add @smcllns/angel-core
pnpm exec angel

    Proof: a usage: line naming exactly build, publish, deploy. It runs under Bun.

  2. 2

    Take the two management credentials

    ANGEL_MANAGEMENT_TOKEN is a bearer. ANGEL_ACCESS_TOKEN is a Cloudflare Access service token as JSON with exactly cf-access-client-id and cf-access-client-secret. There is no self-service endpoint.

    Proof: both set in the shell and in no file.

  3. 3

    Authorize a Google Connection

    In the Access-protected dashboard: save a Provider App (your own Google OAuth client — the secret stores write-only), then walk Google's consent screen and give the Connection a nickname.

    Proof: the Connection reads healthy, with a nickname you will use in angel.json.

  4. 4

    Author the Angel

    angels/<slug>/ANGEL.yaml is portable policy — no targets, no secrets. angels/<slug>/angel.json is local deployment config and stays untracked. 

    {
  "target": "$CONTROL",
  "account": "acct_…",
  "angel": "<slug>",
  "bindings": {
    "preview":    { "gmail": "<nickname>", "docs": "<nickname>" },
    "production": { "gmail": "<nickname>", "docs": "<nickname>" }
  }
}
    preview, not staging — see blocker 2 in the session sheet. The docs you are reading say otherwise and are wrong.

    Proof: name in the YAML matches the directory name.

  5. 5

    Build the Version

    pnpm exec angel build <slug>

    Proof: build/angel.version.json and .sha256 appear, offline. Run it twice — the digest must not move.

  6. 6

    Publish to preview

    pnpm exec angel publish <slug>

    Rebuilds, lists healthy Connections, resolves preview bindings, publishes the immutable Version, installs it in preview.

    Both Angel keys print here, once. Capture them before you scroll.

    Proof: the staged tool list is exactly the operations you wrote — no more.

  7. 7

    Promote the exact staged deployment

    pnpm exec angel deploy <slug> --prod

    Promotes that exact Version and digest under production's own bindings. It does not build, publish, or pick a newer Version.

    Proof: the production digest equals the preview digest you just read.

  8. 8

    Call it over MCP

    curl -sS "$GATEWAY/@<handle>/<slug>" \
  -H "Authorization: Bearer $ANGEL_KEY" \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -H "MCP-Protocol-Version: 2025-06-18" \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'

    Bare coordinate means production. @preview is the only suffix that names an environment; latest and production are rejected.

    Proof: tools/call returns provider data in structuredContent and two redacted receipts — gateway and broker — in _meta. Two receipts or the call did not really pass.

Acceptance. An agent holding only the production Angel key can initialize, tools/list, and tools/call against production and get real Google data back. Nothing else counts, and no repo is needed to prove it.

What I want back

Pass or fail is the least useful thing you can tell me. These seven are worth more than a green run.

  1. Where did you stop trusting the docs? Name the sentence, not the section.
  2. Did the agent try to clone the repo? If so, what sentence made it want to? That is a docs defect, not an agent one.
  3. What did you have to already know? Anything you supplied from memory is a hole in the published path.
  4. When something failed, did the error say what to do next — or only what went wrong? That is the exact class of bug in #27, and I expect more of it.
  5. Did you ever lose track of which environment you were looking at? Preview and production diverging quietly is the failure I most expect.
  6. Was the one-time key reveal survivable? If you lost a key, say so — the recovery story is unwritten and I need to know it hurts.
  7. Could you explain the finished thing to someone else? If the sentence you reach for puts the Angel in the driving seat, the product's own words are not landing.

How to record friction — pick one

Tap to rotate.

One issue per friction, as you hit it

Stop, file, continue. Matches the definition of done literally and nothing gets lost. Costs you the flow of the run, and the first three will be titled better than the last ten.

One running log, split afterwards

A single scratch file with a timestamped line per snag. The run stays honest because you never stop to write prose. I turn it into issues after, and you review the titles. Risk: a line that made sense at the time reads as nothing an hour later.

Record the terminal, say it out loud

script dogfood.log plus a voice memo running. Catches the hesitations that never reach a written note — the ten seconds spent deciding what a message meant is the finding. Heaviest to review.

Two blockers before step 6

Blocker 1 · verified

The npm age gate refuses the CLI

pnpm add @smcllns/angel-core in an empty directory fails with ERR_PNPM_NO_MATURE_MATCHING_VERSION. Your pnpm wrapper sets minimumReleaseAge=10080 — seven days — and 0.3.0 published on 2026-07-29. The product repo exempts it in pnpm-workspace.yaml; an empty directory has no such file.

Fix, verified to install 0.3.0:

# pnpm-workspace.yaml, in the new project
minimumReleaseAgeExclude:
  - "@smcllns/angel-core"

That fix is itself a finding: any stranger following SKILL.md on a hardened pnpm hits this for a week after every core release, and no doc mentions it.

Blocker 2 · verified

The published docs print a bindings key the CLI rejects

Core 0.3.0's config parser throws on a legacy file: angel.json bindings.staging is now bindings.preview: rename the key. SKILL.md step 4 and user-manual.md:293 both still print "staging". Copy either verbatim and angel publish hard-stops.

Fix while running: write "preview". Fix properly: a docs sweep of the seven staging occurrences in SKILL.md and five in user-manual.md, then a docs redeploy. Not yet ticketed — I can raise it before you start if you would rather not meet it.

Conflicts

The served docs conflict with the shipped CLI. Blocker 2 above. §0 lists staging under "never say", and the two documents an agent is told to read say it twelve times between them.
"Retired at cutover" is not what the wire does. §0 calls staging the legacy route name, retired. On the live system the legacy MCP route answers, and the spelling-neutral management routes answer in the legacy dialect unconditionally. The table governs prose and the wire keeps its dialect — defensible, but nowhere written down, so a reader of both gets whiplash. One sentence in §0 exempting the wire would settle it.

True of the build, absent from the APRD

The management dialect is per-route, not per-version. GET/PUT /v1/accounts/{acct}/angels/{slug} answer in staging whatever the caller does; environment-segment routes speak preview. S1 describes the legacy dialect as a compatibility shim for a pinned CLI and does not say it is unconditional on some routes. Anyone driving raw curl needs this.
The docs site cannot drift, and that is a real commitment. build.sh copies the dashboard shell verbatim under two mechanical edits, checks three markers, and generates the fixture with production projection code — so a read-model change fails the docs build. Flow F describes the outcome; nothing states the invariant as something the builder is held to.
The interim-host rewrite covers two files. DOCS_BASE_URL rewrites llms.txt and SKILL.md; every other served document relies on relative links. Load-bearing until #6, and unrecorded.
Google grants expire on a clock, not just on revocation. E9 covers revoke and reauthorize as deliberate acts. The External-Testing seven-day expiry is neither, and it is what will actually interrupt a multi-day run.

One decision I need — where the APRD lives (#30)

The R2 copies went stale twice in an afternoon because two things claim to be the document. Tap to rotate.

Internal only, shared by capability URL

The repo owns it; R2 holds a copy you re-upload when you want to send it. Staleness stays possible but becomes your explicit act rather than a build's omission. Cheapest, and honest about who reads it.

Part of the docs site, built at deploy time

Same treatment as /demo/: build.sh copies it, so it cannot go stale and there is no second copy. Costs you a target-state document being publicly readable — including its open questions and its list of suspicious code.

Repo only; retire the hosted copies

Close #30 by deleting the R2 objects. Anyone who needs it reads it on GitHub. Nothing to keep in sync, and the rendered toggle — the thing that makes it readable by the product team — is lost.

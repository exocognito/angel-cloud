1 · Owner expectations

Specific products the laws must compose into

These are proposed in Sam’s voice for Sam to edit. The boundary text keeps each example honest. A scenario is not achieved until its named dogfood proof passes.

S1 · proposed owner wording

The fresh first Angel

“From a blank machine and new identity, I can use public docs—or ask a fresh agent—to create an Angel, run it locally, publish it to Angel Cloud, inspect it in www, use it in production, verify what it can and cannot do, then delete everything and restart without admin help.”

Boundary
Round 2 supports CLI and max-agent setup plus read-only www. Human authentication, consent, and final inspection stay human. “Delete everything” means the O6 cloud cascade once approved; independent local files and tokens remain separate. Self-hosting is not implied.

Destination WS2 → M2

Proof Fresh-agent preflight and Sam dogfood both complete local and managed paths, prove cleanup, and save evidence.

Guarantees G02 G03 G08 G10 G11 G12 G13

S2 · proposed owner wording

Draft, never send

“I can give my agent a Gmail Angel that creates a draft for me while send and delete are not capabilities it can discover. I can see proof that both gates agreed before Google was called.”

Boundary
This proves fidelity to the reviewed policy, not that the policy is wise or that hosted execution is mathematically attested. Provider credentials remain outside the agent.

Destination WS2 → M2

Proof A real generated Gmail draft exists; send/delete are absent; both receipts agree; local and managed checks pass.

Guarantees G04 G05 G06 G08

S3 · proposed owner wording

A useful multi-App assistant

“I can eventually ask my existing agent to prepare a real task across selected Apps—for example read a calendar, look up a route, draft an email, and update a planning document—while each Angel exposes only the actions and accounts I chose.”

Boundary
Provider breadth, browser/mobile writes, hosted OAuth, billing, and easy self-hosting are later outcomes. No milestone may claim this whole scenario until each provider shape and composed policy passes live proof.

Destination WS3 and later

Proof A later dogfood milestone completes the generated multi-provider task with per-provider live acceptance and no unlisted action.

2 · Final product guarantees

The target laws, their human meaning, current evidence, and limits

These are the target product constitution, not a claim that every capability exists today. Each card separates the law we intend to preserve from the evidence we have now.

target law

G01 · Angel is a toolbox, never an actor

Only the user’s agent initiates an MCP call; Angel has no loop, intent, scheduler, or mailbox.

What this means to Sam
Nothing happens until my own agent asks for a specific tool call.

Current evidence
Demonstrated

Boundary
Angel does not supply the agent or decide what task to attempt.

target law

G02 · Policy stays portable and readable

ANGEL.yaml contains charter and policy, never target, Account, Connection, or credential identity.

What this means to Sam
I can read the file I am approving and reuse it with a different deployment.

Current evidence
Demonstrated

Boundary
Private deployment choices stay in separate config and custody state.

target law

G03 · Builds are deterministic and secret-free

The client compiles canonical immutable bytes; no server builds user source.

What this means to Sam
The same approved source and engine produce the same reviewable bundle without my secrets inside it.

Current evidence
Demonstrated

Boundary
A browser compiler may run on my device; Control may store owner-only drafts but never compiles them.

target law

G04 · Authority is explicit

Absent tools do not exist; guards bind arguments; anything unexecutable cannot publish.

What this means to Sam
If send is not in my Angel, my agent cannot discover a send tool. If I cap an argument, the cap applies before the provider call.

Current evidence
Demonstrated for current adapters

Boundary
The platform proves fidelity to policy; it does not judge whether I chose a wise policy.

target law

G05 · Two gates fail closed

Gateway and Broker decide independently; disagreement or partial install produces no provider call and no fallback.

What this means to Sam
If the two checks disagree, nothing happens.

Current evidence
Demonstrated

Boundary
Availability may fail during disagreement; the system never recovers by using older authority.

target law

G06 · Credentials go in and never come out

Only the unaddressable Broker can lease provider credentials; APIs return safe summaries only.

What this means to Sam
My agent can use an allowed action without receiving my Google token or OAuth client secret.

Current evidence
Demonstrated for managed Google custody

Boundary
Provider identity labels may be shown where I or my agent must choose an account; credentials never are.

target law

G07 · Other tenants do not exist

Cross-Account resources are indistinguishable from absent ones; selectors choose one Connection and omission never fans out.

What this means to Sam
Another customer cannot discover my Angels or accounts, and one call never silently acts on every linked account.

Current evidence
Deterministic tests pass; second real identity waits for M2

Boundary
Multi-account choice requires an explicit opaque selector; multiplayer comes later.

target law

G08 · The same trust object runs locally and remotely

Bundle digest and engine pin travel through publish, verify, receipts, and replay; the product states where proof ends.

What this means to Sam
I can compare my local bundle with production and spot-check cloud decisions against my local engine.

Current evidence
Partial: digest exists; local serve, verify, engine pin, and replay are WS2 work

Boundary
Artifact identity is client-checkable. Remote execution remains trusted and bounded by receipts/replay, not fully proved.

target law

G09 · Release defaults stay simple and safe

Bare publish means production; preview is explicit, isolated, and exact-byte promotion never rebuilds.

What this means to Sam
My first publish can go live in one clear step; if I ask for preview, it does not silently use real production accounts.

Current evidence
Demonstrated; stale surfaced copy remains housekeeping

Boundary
Preview remains an advanced option with separate bindings or an explicit credential-share choice.

target law

G10 · Owners control the full lifecycle

Keys are shown once and recoverable by safe rotation; pause only removes; deletion is deliberate, total, and self-service.

What this means to Sam
I can recover a lost Angel key, turn authority off, delete my cloud Account, and start fresh without an operator.

Current evidence
Partial: Angel keys/pause/delete work; Account deletion is O6 + WS2

Boundary
Exact Account-deletion scope is still O6; local files/tokens stay independent from cloud deletion.

target law

G11 · Trust evidence is public without private identity

Every live Angel exposes a secret-free trust page and review bundle, never credentials or Connection identity.

What this means to Sam
Before connecting, I—or another agent—can inspect what the Angel exposes and what artifact it runs.

Current evidence
Partial: basic trust page works; full review bundle is O7 + WS2

Boundary
The minimum public bundle and exclusion list are still O7; private account identity never becomes public proof.

target law

G12 · One product spans CLI, browser, and agent

The surfaces share one policy, compiler, artifact, and job model; public docs suffice and human auth/consent remain human.

What this means to Sam
Whether I type commands, ask an agent, or inspect www, I am working with the same Angel and evidence.

Current evidence
Partial: shared contracts exist; public-doc whole journey failed Round 1

Boundary
Round 2 intentionally keeps www read-only; full browser/mobile authoring is later.

target law

G13 · Local use is independent; hosting is optional

Local create/build/connect/serve needs no Angel Cloud account; managed and self-hosted custody stay separate.

What this means to Sam
I can use an Angel locally without signing up for Angel Cloud, then choose managed hosting with separate consent.

Current evidence
Target: local serve is WS2; managed exists behind side doors; supported self-hosting is unproved

Boundary
Supported self-hosting is not shipped; O9 decides whether Round 2 shows status only or adds a proof.

target law

G14 · Source and deploy topology stay bounded

One repo may hold many packages/apps, but core/CLI packages, deployables, Cloudflare accounts, bindings, and secrets remain separate.

What this means to Sam
Agents can change the product coherently in one repo without merging security or deployment boundaries.

Current evidence
Decided, not built: monorepo is INT-03

Boundary
Monorepo means one source history, not one package, Worker, Cloudflare account, or secret store.

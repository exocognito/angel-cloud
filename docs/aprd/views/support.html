The page you keep open while answering a ticket

Angel Cloud gives one person a small, provable toolbox for their AI agents. Most tickets are one of about a dozen known situations — and roughly half of them are the product working exactly as designed. This page tells you which is which, what to say, and when to escalate.

Ground rule: the system fails closed. A refused call is a nuisance; a wrongly allowed one is a betrayal. So when a user reports "it refused to do X", start from the assumption that the refusal is correct and specific — every error below has exactly one meaning.

How it works in 60 seconds

Five steps. Every ticket lands somewhere on this line, so place the ticket first, then diagnose.

  1. 1 · Write

    The owner writes a short policy file: which operations the agent may call, with guards on arguments. Anything not listed does not exist.

  2. 2 · Publish

    One CLI command builds it and makes it live. What you can't run is refused at publish or deploy — not days later mid-task.

  3. 3 · Key, once

    Each environment gets a bearer Angel key, shown in plaintext exactly once. The server keeps only a hash. Nobody — including us — can read it back.

  4. 4 · Connect

    The agent talks to one MCP endpoint with that key. It sees only the allowed tools; a paused or absent tool isn't "blocked" — it's not in the list.

  5. 5 · Double-check

    Every executed call is checked by two independent gates, each writing a tamper-evident receipt. If they ever disagree, the call simply doesn't happen.

Troubleshooting table

One row per failure a user can hit. The status pill tells you at a glance: by design means the product is doing its job, user-fixable means walk them through it, escalate means it's ours.

What the user reports What it actually means What to tell them How it gets fixed
"My agent gets 401 / unauthorized." user-fixable Missing or wrong Angel key (401 / -32001), rejected before the request body is even read. Common cause: a preview/staging key presented to production — environment keys never cross. "Your key doesn't match this environment. Check you pasted the production key to the production endpoint — a preview key never opens the production door." Paste the right key. If the plaintext is lost, it's gone — Rotate on the Agent Keys pane mints a replacement and kills the old one. See the key clinic below.
"My agent says the tool doesn't exist." by design unknown_tool: the operation is absent from the deployed policy. Example: an inbox-read Angel whose agent asks for messages.send — send was never in the toolbox, so there's nothing to call. "That's the product working. Your Angel only contains what you put in it — a forbidden action isn't blocked, it doesn't exist." If they genuinely want the capability: edit ANGEL.yaml, publish a new Version, promote. Authority is never added at runtime or by support.
"It asked which account and my agent failed." by design connection_required: the tool is bound to more than one Connection (say personal and work Gmail) and the agent omitted angel_connection. The platform never guesses and never fans out to all accounts. "You have two accounts connected, so every call must say which one. The agent picks from a menu titled like 'gmail - work account'." The agent includes the angel_connection value from tools/list. With exactly one Connection, omission is fine — this only appears once a second one exists.
"It worked yesterday, now it says the connection is unavailable." user-fixable connection_unavailable: the agent cached an arc_… selector from before a redeploy. Selectors are minted fresh for each deployment, so the old one is stale — not broken, expired. "Nothing is wrong with the account. Your agent is using an old selector from before the last deploy; it needs to refresh its tool list." The agent calls tools/list again and uses the new selector. Any agent that caches selectors across deploys will hit this every deploy.
"It says paused" / "a tool disappeared from my agent's list." by design connection_paused: that tool + account pair is paused (the tool's other accounts still work). tool_paused: no active Connection remains — and a fully paused tool vanishes from tools/list entirely, which users read as "it disappeared". "Someone flipped a pause toggle — often Pause all before a holiday. Disappearing from the list is intentional: a paused tool isn't shown as callable." Allowed Tools pane → resume the tool or the tool + Connection toggle; or Settings → Availability → Resume all. See the pause gotchas below before advising Resume all.
"It refused to move a message to Trash." by design guard_denied: an argument guard rejected the call. Example: a policy allows messages.modify but forbids the values TRASH, SPAM, SENT — so relabel and archive work, trashing is refused with a receipted reason. "Your own policy forbids that exact argument. The agent can relabel and archive; it provably cannot trash. The refusal is logged with a reason — that's the audit trail working." Nothing to fix unless the owner wants the guard loosened — which goes through source: edit the guard, publish, promote. Support cannot loosen a guard.
"HTTP 500 — 'Angel gates failed to converge'." escalate -32603: the two independent gates disagreed, so the platform refused the call rather than pick a winner. No provider call was made. This status is intentional — fail closed — but the disagreement itself is a platform fault. "The safety system caught an internal inconsistency and stopped the call — your data was not touched. This one is on us." Escalate with the request ID from _meta. Not user-fixable; the receipts on both gates let engineering see exactly where the decisions diverged.
"Calls suddenly fail with a provider error." user-fixable -32003 family: a provider or custody failure — most often a revoked Google grant. The Connection is marked error on the dashboard and the platform fails loudly rather than pretending. (Also expected weekly while the OAuth app is in External Testing: refresh tokens expire after seven days.) "Google cut off the grant — usually a revoke or an expired test-mode token. Nothing about your Angel changed, and nothing needs reconfiguring." Connections page → the row showing error → Reauthorize. The same Connection comes back healthy — same nickname, same identity, deployment and keys untouched. Calls pass again immediately.
"I get 405 / 406 / 415 / 403 from the endpoint." user-fixable Client transport misconfiguration, each with one meaning: 405 = non-POST (the endpoint answers Allow: POST); 406 = Accept missing application/json + text/event-stream; 415 = wrong Content-Type; 403 = a foreign Origin header; 400 = missing MCP-Protocol-Version after initialize. "Your MCP client is configured slightly wrong — the specific status tells us exactly which header. This is a setup fix, not an outage or a permissions problem." Fix the named header in the agent client and retry. These never involve the policy, the key set, or the account.
"My publish/deploy command returns 409." user-fixable A management conflict, three flavors: an Idempotency-Key reused with a different body; a stale expectedDigest (the staged deployment moved under them); or a pending repair marker from an interrupted change, which blocks every different mutation until repaired. "The platform refused rather than guess. If a change was interrupted: retry the identical request and it completes the repair. If the digest is stale: something changed since you last looked — re-read state and retry deliberately." Interrupted change → retry the byte-identical request. Reused idempotency key → mint a fresh key for new input. Digest drift → re-fetch, confirm intent, resend. Retrying is always safe: it can never double-fire.
"I can't delete a Provider App — it returns 501." by design 501: Provider App removal is not implemented in this milestone. The API reserves the route and says so honestly instead of half-deleting. "Not built yet — deliberately, not broken. Your Connections and Angels are unaffected; the stored client secret stays write-only either way." Nothing to do today. Note the request; removal is on the deferred list.

Key lifecycle clinic

Four facts settle almost every key ticket. Say them plainly.

Shown exactly once

The plaintext appears one time — at creation, mint, or rotate — beside the only Copy control, with a save-it-now warning. After that the server holds only a hash and a short fingerprint. No API, no admin, no support request can read it back. "Can you look up my key?" — the honest answer is that nobody can.

Lost key → rotate

A lost plaintext is unrecoverable, but never a crisis: Agent Keys pane → Rotate mints a replacement and reveals it once. The old key stops working the moment you rotate — warn users with several agents on one key that all of them need the new one.

The last key can't be revoked

Revoking the last active key would lock the environment out entirely, so the platform refuses. A user who "can't revoke this key" almost always has exactly one left. Mint a new key first, move agents over, then revoke the old.

Deploys never change keys

Publishing and promoting a new Version leaves every key untouched — only explicit mint, rotate, or revoke changes the key set. So "we shipped v3 and the agent broke" is never a key story; look at the policy diff or a stale arc_… selector instead. Responses carry x-angel-version so you can confirm which policy served the call.

Pause and resume — the four ticket generators

Pauses survive a deploy — but a pause whose target is gone does not. A deployment mints fresh arc_… selectors, so the platform remaps every per-Connection pause onto the new deployment by Connection, not by selector. Tool-level pauses are pruned to the tools that still exist; a tool + Connection pause is dropped only when that Connection is no longer bound to that tool. Example ticket: "I paused my work account on the archive tool, we shipped v4, and the work account is active again." Check the new Version first — if it stopped binding work Google to that tool, the pause had nothing left to hold and was dropped. Re-bind, or re-apply the pause.
Resume all clears every override. Pause all and Resume all reset the environment default and wipe every per-tool and per-Connection override. After a Resume all, nothing stays paused — including the one tool the user carefully switched off last month. Before advising Resume all, ask whether any pause is meant to be permanent; if so, resume tools one by one instead.
While the environment default is paused, new tools inherit paused. A user who paused everything, then shipped a Version adding a tool, will report "my new tool never appeared". It deployed fine — it inherited the paused default and is waiting for a resume.
Paused tools vanish from the agent's tool list entirely. Not greyed out, not "disabled" — absent from tools/list. Users report this as "the tool disappeared" or blame their agent. A direct call to the vanished tool returns tool_paused or connection_paused, which confirms the diagnosis in one request.

One more distinction worth saying out loud: pause is a reversible last-mile overlay that can only switch things off. It never adds a tool or loosens a guard. Removing authority for good goes through source — edit, publish, promote.

Known issues — one live, one worth remembering

#1 · Promotion breaking connection-scoped availability overrides — fixed. The one ticketed correctness bug in the enforcement path; it took production down about four minutes on 2026-07-27 and is now closed. Worth keeping in your head because the symptom is memorable: an environment went dark immediately after a promote, on accounts that had a tool paused everywhere and switched back on for one Connection. That re-enabling setting was attached to an identifier a new release replaced, so it went missing at the worst moment. Pause settings now follow the Connection across a release. If you see this symptom on a current deployment, it is not this bug — escalate it as new, with the Angel and the promotion time.
Admin reset paints fabricated healthy Connections. The admin reset endpoint currently seeds fake "healthy" Google Connections over real custody state. Classified a bug on 2026-07-28; it will stop. Until then: after any reset, dashboard Connection health is not evidence — a "healthy" pill may be fiction. Verify with a real call, not the pill.

What to escalate, what to self-serve

Self-serve — walk them through it

  • Rollback. No rollback command exists. The path is re-promotion: publish the old source again, stage it, promote that exact staged Version. Same safety rules, just manual.
  • Revoked Google access. Row-level Reauthorize on the Connections page — the same Connection returns, nothing else to touch.
  • Lost or leaked keys. Rotate (lost) or mint-then-revoke (leaked, when other agents share the key).
  • Interrupted changes. Retry the identical request; a repair marker completes and the 409s stop.
  • Any authority change. Edit ANGEL.yaml, publish, promote — support never edits policy for a user.

Escalate — or set expectations honestly

  • Any -32603 convergence failure. Platform fault by definition. Collect the request ID and escalate.
  • Environment dark right after a promote. This is what issue #1 used to do, and it is fixed — so a report of it now is a new fault, not that one. Escalate with timing; don't troubleshoot the user.
  • Activity history requests. No retention, search, or export guarantee exists yet. Never promise "we can pull the logs from last month."
  • "How do I sign up?" There is no signup — one pre-provisioned Account behind Cloudflare Access. Say so; don't waitlist people informally.
  • Naming heads-up. "Staging" is now "preview" — the dashboard, the docs and the platform all say preview. The published command-line tool still says staging, and old /v1/a/…/staging/mcp endpoints still answer, so a user pasting CLI output or an old URL will show you the old word. They mean the same environment. Translate silently; don't make the user care.

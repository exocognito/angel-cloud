Angel Cloud

Your agent drafts the email.
It provably cannot send it.

An Angel is a small toolbox you hand the AI agents you already use — it replaces none of them. The toolbox holds only what you put in it — the forbidden action isn't blocked, it doesn't exist. Every action the agent takes is checked twice and leaves a tamper-evident receipt.

The draft-but-never-send toolbox is the flagship acceptance test for the next milestone in build. The enforcement machinery beneath it — two gates, receipts, argument guards, credential custody — is live today shipped.

This page is the marketing rendering of the Angel Cloud APRD. Every claim on it traces to the dataroom or the public FAQ; the guardrails section below says exactly what we may and may not claim in the market today.

The story in three sentences

1

The forbidden action doesn't exist

An Angel exposes only the operations its owner allowlisted, with argument guards. Ask a read-only inbox Angel to send an email and there is no tool to call — messages.send is absent from the toolbox, not merely refused. shipped

2

Enforcement is compiled, not prompted

The rules are compiled from a reviewed source file. No model, no prompt, no runtime config sits in the enforcement path — so there is no AI judgment call to sweet-talk, and production runs byte-for-byte what the owner published. shipped

3

Every action leaves a double-checked receipt

Two independent gates evaluate every call; each writes a hash-chained receipt; the call succeeds only when both decisions converge. If they ever disagree, the action simply doesn't happen. shipped

The flagship moment

You watch a draft appear in your Gmail, written by your agent — and you know, not hope, that "send" isn't in its toolbox. The draft operation passes both gates and returns two receipts; the send operation returns unknown_tool because it was never compiled in. That single moment is the whole product promise. in build — acceptance test E15, milestone M2

Why this is different — honestly framed

Each comparison below states the mechanism that licenses it, and states the limit of the claim. Marketing that outruns the mechanism gets walked back later; this framing doesn't.

Versus OAuth scopes alone

Scopes are too coarse: a single Gmail scope can permit several operations when you need exactly one. An Angel narrows below any single scope — a compiled allowlist plus argument guards. Example: an Angel that allows relabelling messages but forbids the values TRASH, SPAM and SENT — so an agent working through it can file a message and cannot bin it.

The honest boundary: the provider credential inside custody is still as powerful as its OAuth grant. The claim is that the agent-facing path exposes and enforces less authority — not that OAuth itself got narrower.

Versus a hosted Gmail MCP server

A hosted MCP server over Gmail constrains the tools, not the credential. A broad grant like gmail.compose authorizes messages.send — so the token behind such a server can do more than its visible tools suggest, and safety rests on which tools happen to be shown. It also gives you no argument-level guards, no tool subsetting you control, and no tamper-evident audit. An Angel gives you both halves: the forbidden operation is absent from the toolbox, and the credential stays in custody, bounded by the compiled allowlist.

What two gates buy

The Gateway and the Broker each evaluate policy, guards, availability, and account selection from scratch; the inner gate does not trust the outer one. A bug or compromise in either enforcement path fails closed instead of slipping through, and both gates' receipts must agree before anything executes.

The honest boundary: the two gates are not independent administrative trust domains, and they share decision code — a shared bug can affect both. Deliberately diverse gate implementations are deferred. See the guardrails below before claiming otherwise.

The vault with no front door

The credential vault has no public URL — the Broker is reachable only over internal service bindings, never a hostname. Credentials are write-only: envelope-encrypted per account, leased only inside the Broker, never returned by any API. Once you hand over a credential, no one — including you, including us through any API — can read it back out. It can only be used, inside the vault, for allowed calls.

The coordinate is the brand upcoming

Every Angel gets one canonical address: @handle/angel. One spelling, no variants, short enough to say out loud — "at acme slash inbox-read". The plain address always means the live version, and a name you've seen can never quietly come to mean someone else's Angel: handles are never released, and old links keep resolving to the same owner.

What the coordinate becomes

@acme/inbox-read

  • The MCP endpoint an agent calls — paste it into any agent app.
  • A public page anyone can read — no key, no login — showing what the Angel allows before deciding to trust it. Nothing on that page can reach a credential or a session, by invariant.
  • A citation: "read the charter at the coordinate" becomes a real sentence.

Status: the coordinate grammar and handle rules are specified; the public page is designed-for but not shipped, and its exact content is a deliberately open decision. Say "upcoming", never "live".

Install paths are plural: npm now, a curl installer next. Cloning the repo is one path, never the interface. And a practice-run mode (preview) exists for those who want it — it never silently touches real data; using real accounts in preview requires saying so in so many words.

Claim guardrails — what we can and cannot say

The working list for any copy, deck, or post. Red is a claim that would be false or would outrun the product today; its pair is the honest version that still sells. When in doubt, the dataroom wins.

Word-level rules live upstream of this page, in the dataroom's terminology table (§0) — what each term means, the phrasing to use, and the phrasing that plants a false idea. Check a new line against that table first; these pairs are the market-facing application of it, not a second rulebook.

Cannot say

"An Angel drafts / reads / answers for you" — anything casting the Angel as an assistant, an actor, or a replacement for the user's agent

Can say

"Your existing agents work through an Angel." An Angel never acts on its own — it is the toolbox that bounds what your agents can touch. Every sentence should keep the agent as the actor and the Angel as the boundary.

Cannot say

"Sign up today" / "Try it now"

Can say

"Access is invite-only and operator-provisioned in this phase." There is no signup, waitlist, or public catalog. Self-serve signup is an explicit later milestone.

Cannot say

"Enterprise-grade uptime", "SLA", "24/7 support", or any reliability number

Can say

"When in doubt, the system fails closed — a refused action, never a wrongly allowed one." Sell the safety posture, not service guarantees that don't exist yet.

Cannot say

Any price, plan, quota, or rate limit — even "generous free tier"

Can say

"Pricing isn't set." One true cost claim exists: making ten more Angels costs the owner nothing to operate — the platform runs three Workers total, constant as Angels multiply.

Cannot say

"Always-on monitoring of your Google account" or any durable-connection claim

Can say

"Real Gmail and Docs calls are proven live." The Google OAuth app is still in External Testing, so refresh tokens expire after seven days — valid short-term proof, not a durable monitor. Say "proven", not "always-on".

Cannot say

"For your team" / "share with your family"

Can say

"Built to run one person's real life first." Team roles and Family Accounts are deliberately sequenced later — the product must prove itself for one person before it multiplies.

Cannot say

"Works with any API" / "call it over REST"

Can say

"Agents talk to Angels through MCP — one standard protocol, deliberately the only way in." A second surface would be a second thing to secure; REST is reserved, not built.

Cannot say

"Two fully independent security domains" / "nobody can access your credentials"

Can say

"Two independent checks on every call — and we're honest about the limit: both run in one Cloudflare account, so a Cloudflare administrator who can replace the Broker could reach custodied credentials. Buyers for whom that matters most should self-host relay, and we say so."

Also unanswerable today — decline gracefully, don't improvise: data residency and compliance, MCP setup recipes for specific agent apps, the tool catalog beyond Gmail and Docs, activity retention/search/export guarantees, and recovery from a lost key beyond rotating to a replacement.

Message-map candidates proposals — not decisions

Three positioning angles, each anchored to the mechanism that keeps it honest. Tap or swipe to rotate.

Angle 1 · The absence claim

The forbidden action doesn't exist.

Other tools block dangerous actions. An Angel never compiles them in — there is nothing to jailbreak, because there is nothing to call.

Mechanism: the build strips everything outside the allowlist; tools/list returns only the deployed toolbox, and an invented call gets a receipted unknown_tool before any provider request.

Angle 2 · The flagship demo

Your agent drafts. It provably can't send.

Give your agent real usefulness and keep the one action you'd regret out of its hands — not by policy prose, by construction.

Mechanism: eval E15 — drafts.create allowed and receipted through two gates; messages.send absent from the artifact entirely. (Lead with this only once M2 ships; until then it is "the test we're building toward".)

Angle 3 · The custody claim

Hand your agent a toolbox, not your password.

Your credential never meets the agent. It lives in a write-only vault with no public URL and comes out for exactly one thing: allowed calls.

Mechanism: credentials are envelope-encrypted per account, leased only inside the Broker, never returned by any API; the Broker has no hostname, ever.

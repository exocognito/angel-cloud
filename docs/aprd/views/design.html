The design brief, sorted by what binds you

Everything here is derived from the dataroom. Some UI moments are normative — the product promise depends on their exact shape, and you design around them, not over them. Other surfaces are open — deliberately unsettled, waiting for design work. Mocks on this page marked illustrative are suggestions, not requirements.

Binding

Open — yours to design

1 · The dashboard, as deployed

Start here — or rather, start here soon. This is meant to be the public demo: the real www/ shell filled with generated sample data, nobody's account, no login. The frame below is blank, and will stay blank until two things land. The step that assembles the page from www/ at deploy time, so it shows the current product rather than an old picture of one, arrives with #21: the docs site ships today but its build copies markdown only. The address it points at resolves once the angelmcp.ai zone moves (#6). The dataroom tags flow F an intended change for the same two reasons. Nothing you click will touch the live system. 2 · UI moments the design must honor

Each of these carries a product promise. Restyle them freely; never soften, relocate, or remove the behavior.

One-time key reveal normative

A plaintext key appears exactly once — at creation, mint, or rotate — beside the only Copy control, with a save-it-now warning. The server keeps only a hash and fingerprint; no API can ever show the key again. So the resting key list shows •••• + last-3 fingerprints (e.g. ••••415) with Rotate and Revoke — and no per-row Copy, ever. The last active key cannot be revoked.

Production key — shown once

ak_production_9f2kq81xm3… Copy

Save it now — it will not be shown again.

Preview refusal names its two remedies normative

Preview binds its own Connections; it never inherits production's. A preview publish with no preview bindings must fail and offer exactly the two honest ways forward. The flag spelling is indicative; the two-choice structure is not.

✗ preview has no Connections bound
Either:
  1. bind a Connection to preview in angel.json, or
  2. explicitly share production's: --share-production-credentials

Delete a live Angel: retype its name normative

When production has a live or pending deployment, deletion requires the typed slug. When production is empty, or only preview is deployed, no confirmation. Delete is hard and total — keys revoked first, both environments torn down, coordinate 404 — and the slug is immediately reusable. The API does all of this today; only the command that calls it is missing, so a dashboard delete control would have a working backend the day it is designed.

"Created new Angel" announced before keys print normative

Publishing a name that doesn't exist creates it — never renames. Creation must be announced before any key is shown, so a typo can't silently mint a duplicate Angel and hand you its keys as if it were the one you meant.

Policy denials are calm; degraded states are loud normative

A rule blocking an action is the product working: agents get HTTP 200 with a machine-readable denial reason, and the dashboard treats denials as normal in-flow events — never as crashes or alarms. The opposite holds for availability: when an environment is degraded (frozen, gate drift, pending repair), the warn/danger banner stays loud on the Angel's front door. Healthy states stay quiet. Do not invert this hierarchy.

3 · New feedback: the list view hides half the story

Owner · 2026-07-28

The Home list density leads with tool chips — labelled "what it can do" in the shipped UI, itself a phrase §0 would not allow today — and gives no column to the accounts and Connections an agent may act as through an Angel. But which identities an agent may act as through it and which tools it may use are co-equal, different, top-level facts. The list view must present both. Fold into the next dashboard design pass.

4 · Open design decisions — do not settle here

The dataroom leaves these open on purpose: a prior decision (PD 0003) got reversed same-day because it was made before there was a real thing to look at. Explore; don't commit.

Retired-handle visibility open

After a rename, old MCP addresses answer in place — that part is live. Old page links will 301 to the new handle, once pages exist. Whether — and how — the UI surfaces "this handle was retired" is undecided. Decide before public signup (M3).

Lookalike handles open

Confusable pairs (rn/m, 1/l) are unhandled. Fixed inputs a future design inherits, all enforced in code today: four to thirty-two characters, the fourteen authority words reserved, handles never released. Decide before M3.

5 · Prototype parity digest

The shipped UI deliberately diverges from the reference prototype where the backend can't back the prototype's assumptions. Update the mockup to match; none of these are bugs.

Banned surface

No "+ New angel" row, anywhere. Creation is a CLI journey, surfaced by the zero-Angel Home guide; an in-app row would be a dead end and the IA contract bans it.

Key rows

No per-row Copy; keys can't be re-displayed. Identifiers are •••• + last-3 hash fingerprints, not key_live_… shapes. Copy exists only on the one-time reveal.

No fleet "Pause all"

No backend action pauses everything. Pause/resume is per-Angel, per-environment, on Settings → Availability.

Activity chart

Omitted — no backend produces the counts yet. Keep it in the mockup as future state; the CSS keeps the component reserved.

Group labels

Real tool.group values, counted "N read" / "N allowed", with a provider-level READ-ONLY badge for fully read-only providers.

Tab renames

Config → Allowed Tools; MCP & Keys → Agent Keys. Activity and Settings unchanged.

The one live wedge — needs a designed home

A wedge is a dashed amber block marking real product data the approved mockup has no home for. Exactly one exists: the per-environment Version line on each Home dashboard card. It is the backbone of exact promotion — what runs where, and whether a promotion is ready — and must stay visible from Home. Give it a designed home so it can shed the wedge treatment.

prod version 3 · preview version 4 · Version 4 ready for exact promotion — not in the design yet

Back-office relocations — know they exist

  • Per-Version sha256 digests → Settings → Version history. The front door shows no digest.
  • Gate alignment, bindings-available, availability revision → Settings → Availability.
  • Exception, by design: degraded availability stays loud on the front door (see section 2).

Public Angel page

First surface strangers ever see. Constraints: no key, no login, no path to credentials. Content open — see section 4.

Handle selection

Operator-set today; a signup step at M3. Fixed rules the flow must carry, all enforced in code already: unique forever, never released, one rename per Account ever, four to thirty-two characters, the fourteen authority words reserved. "One rename, ever" needs real weight in the UI — the server answers a second attempt with a flat refusal, so the interface has to have said so first.

Preview indicator

"Staging" has become "preview" — the dashboard says preview everywhere, and preview binds its own Connections. What is still undesigned: the owner must always be able to tell at a glance which environment they're looking at, and whether preview is sharing production credentials (that sharing is explicit and typed, and the deployment record shows it). The pinned CLI still prints the old word, so error text a user pastes into a ticket may say staging for a while yet.

Coordinate display

Endpoints have shifted from /v1/a/… paths to @handle/angel coordinates — one canonical spelling, bare means production, @preview suffixes preview. The Gateway answers both, and the dashboard already builds its endpoints from the handle. Agent Keys shows the endpoint; Home and the Angel header still need a home for the coordinate as the Angel's say-out-loud name.

The dataroom is normative; where this page and the dataroom disagree, the dataroom wins.

Angel Cloud: the target one-player product

Angel Cloud gives one person provable least-authority toolboxes for their agents. This document is buildable as written: it specifies the target state — coordinates, handles, one-command publish, opt-in preview, delete, public pages, and M2 adapter depth — on top of the shipped two-gate enforcement core. Angel Cloud lets a person hand an AI agent a small, safe toolbox — the agent can do exactly what the owner allowed and nothing else, and the owner can prove it. This document describes the product we are building next: simple names, one-step publishing, safe test runs, deletion, and pages anyone can read.

Precedence: Spine > Evals > System diagram > Prototype > FAQ. The Spine wins all conflicts. Terminology (§0) sits outside that order: it states no requirement, it defines the words the requirements are written in, and it governs how the product is described everywhere. Elements tagged normative bind the builder; illustrative elements do not. observed marks behavior already live in code; change marks intended departures from the live system. The Developer rendering is normative; the User rendering (toggle, bottom right) is derived from it — it states what the end user will notice, written for the product team. 0 · Terminology normative

This section defines the words the rest of the document is written in. It states no requirement, so it sits outside the precedence order — but where any page, commit message, doc, or marketing line uses one of these words differently, this table wins. The Never say column is not style advice: each entry names a specific wrong idea the phrasing plants. It binds this document, the audience views, and anything written from here on. Docs that predate it have not been swept — ROADMAP.md still has an Angel answering MCP, and PD 0003 has one reading a mailbox — so the table is the rule going forward and a backlog of edits behind. These are the words we use and the words we must not use. The right-hand column is the important one — each of those phrases sounds harmless but teaches the reader something false about the product, so it stays out of docs, help articles, and marketing copy. Older docs written before this table still break it in places; those are worth fixing, and nothing new should add to them.

The one that keeps going wrong: an Angel is a toolbox, not an actor. It has no intent, no loop, and no session; it never initiates anything. Every provider call begins as an agent's authenticated tool call. Any sentence with an Angel as the subject of a verb the user cares about — drafts, reads, sends, answers, books, replies — is wrong, and it is wrong in a way that makes the product sound like a competitor to the agent the user already has. The mistake we keep making: writing as if the Angel does the work. It doesn't. Your agent does the work; the Angel is the toolbox you handed it, and what is in the toolbox is the limit of what the agent can reach. Getting this backwards makes it sound like we're asking people to swap out the AI they already use — we're not.

1 · Spine normative

Goals

  1. G1 — Least authority, compiled. An Angel exposes to an agent only allowlisted canonical operations with argument guards; enforcement is compiled from reviewed source, never a model, prompt, or runtime config. An Angel is not an agent and replaces nothing in the user's agent stack: it never acts on its own, and every provider call originates from an agent's authenticated tool call through it. observed The agent's toolbox contains only what the owner put in it. A forbidden action isn't blocked — it doesn't exist. No AI judgment call sits between the agent and the rules. And an Angel is not a new assistant: you keep the agents you already use — they simply work through the toolbox.
  2. G2 — Run one person's real life. M2: Angel Cloud runs one person's real daily workflows across several providers. Gmail write with real guard enforcement first, then Maps, then differently shaped integrations — each adapter ships with guard enforcement, deterministic CI, and live credentialed acceptance. change The product must be genuinely useful day to day for one person — reading and drafting email, looking things up — across several services, not just a demo of two read-only operations.
  3. G3 — Source to live in one command. angel publish takes a fresh Angel from source to a live production endpoint in one step. Preview is opt-in (--preview) and binds its own Connections (PD 0003 + PD 0005). change Publishing feels like publishing: one command and your Angel is live. A separate "practice run" mode exists for those who want it, and it never silently touches your real data.
  4. G4 — Agent-operable journey, meeting users where they are. An agent given only the public docs (docs.angelmcp.ai: index, llms.txt, SKILL.md) can take a user from zero to a live Angel through the management API — no repo access, no human help. Install paths are plural: npm now, a curl installer next; repo clone is one path, never the interface. change A user can say "set me up an Angel" to their AI assistant and it works — even for someone with no GitHub account, using a desktop AI app. Getting started never requires our source code.
  5. G5 — Every Angel is shareable and citable. Every Angel has one canonical coordinate, @handle/angel, and a public page at that coordinate readable without a key or login (PD 0001, PD 0002). change An Angel has a short name you can say out loud and a web page you can send to anyone. People can read what an Angel allows before deciding to trust it.
  6. G6 — Provable enforcement. Two independent gates evaluate every executed call; each writes a hash-chained receipt; a call succeeds only when both decisions converge. Deployments are digest-pinned: production runs byte-for-byte what was published. observed Every action an agent takes is checked twice by separate systems and leaves a tamper-evident paper trail. What runs in production is exactly what the owner reviewed — provably, not by promise.
  7. G7 — Directional (not yet normative). M3: a stranger signs up, connects Google through a platform-owned verified OAuth app, publishes, and is billed within quotas — no operator help. M4: Personal and Family Account shapes; the tenant boundary holds under test. Sequenced strictly after G2. Detail lands in a future APRD revision. Later: anyone can sign up on their own, and eventually families can share an Account. Deliberately last — the product must prove itself for one person first.

Non-goals

  • No code-execution engine. The platform accepts canonical secret-free artifacts; it never accepts source YAML and never runs a user's build.Angel Cloud never runs your code — it only enforces your rules. That keeps the trust story simple.
  • No authoring or publishing from the web UI. Policy enters through reviewed source and the CLI; the dashboard can promote, manage keys, and pause — nothing more.You can't create or edit an Angel's rules by clicking around a website. Rules always come from a reviewable file, so changes leave a trail.
  • MCP is the only invocation surface. REST invocation on api. is reserved, not built.Agents talk to Angels through one standard protocol. A second way in would mean a second thing to secure.
  • Omission never means fan-out: a tool call is never broadcast to every Connection (ADR 0002).If an agent doesn't say which account to use, the platform asks — it never guesses "all of them".
  • The Broker never gets a hostname. Reachable only over service bindings — the credential vault has no public URL, ever.The safe where your passwords-equivalents live has no front door on the internet at all.
  • No per-Angel infrastructure: three Workers total, constant as Angels multiply.Making ten more Angels costs the owner nothing to operate.
  • This APRD does not settle: the public page's content design, opt-in default, preview pages, or content negotiation (#11); lookalike-handle handling; retired-handle visibility. Settling them now would repeat the PD 0003 error — deciding on evidence a prior change invalidates. See FAQ.A few design questions are deliberately left open until we can look at the real thing — noted in the FAQ so nobody mistakes silence for a decision.
  • Not in this horizon: signup, billing, quotas, retention/search/export guarantees, team roles, custom domains, diverse gate implementations, a self-host guide.Later, not now: self-serve signup, payments, long-term activity history, and teams.

Invariants — what must never happen

  1. I1 — Closure. An operation may be published only if its request derivation from a reviewed provider spec is sealed in the artifact and a registered adapter interprets it. Hand-coded per-operation execution paths are forbidden (ADR 0005). observedNothing can be published that the platform can't provably execute from its reviewed catalog — no hidden hand-wired actions.
  2. I2 — Immutability. A Version is never edited or overwritten; promotion installs the exact staged bytes by digest; the same digest republished returns the same Version. observedWhat you tested is what goes live, byte for byte. Published versions can never be quietly altered.
  3. I3 — Convergence. Gateway and Broker evaluate independently; disagreement refuses the call; neither gate ever falls back to an older Version or availability state. observedIf the two checkers ever disagree, the action simply doesn't happen. The system fails safe, never "probably fine".
  4. I4 — Ordering. Install and resume open the Broker first; pause and teardown close it first. Interrupted changes leave a visible repair marker; a different mutation conflicts with 409 until repair completes. observedDuring any change, the system passes through safe states only — a half-finished change blocks rather than half-works.
  5. I5 — Custody. Provider credentials are write-only: envelope-encrypted per Account, leased only inside the Broker, never returned by any API. Only the Broker holds the KEK. Custody failure throws; no fixture substitution. observedOnce you hand over a credential, no one — including you — can read it back out. It can only be used, inside the vault, for allowed calls.
  6. I6 — Isolation. A request for another Account's resource returns 404, never a denial confirming existence. observedOther people's Angels are invisible to you — not "access denied", but "doesn't exist".
  7. I7 — Selection. angel_connection is platform-reserved; the compiler rejects policies defining it; the selector is stripped before the provider is invoked. observedThe "which account?" switch belongs to the platform, so no Angel author can hijack or fake it.
  8. I8 — Nickname boundary. Agents never see Connection nicknames, management IDs, or credentials — only opaque per-deployment refs and provider-derived labels. observedYour private labels ("work gmail", "therapy notes doc") never reach the agent or anyone you share an Angel with.
  9. I9 — Keys. Angel keys are hashed at rest, plaintext shown exactly once, stable across deploys; only explicit mint/rotate/revoke changes the key set; the last active key cannot be revoked. Key names: 1–64 code points, no control characters, on every surface. observed (name bounds on /v1: change)Shipping a new version never breaks connected agents. A key is shown once — save it then — and you can't accidentally lock yourself out by revoking the last one.
  10. I10 — Overlay. The availability overlay can only remove effective availability; it can never add a tool or loosen a guard. Durable authority reduction goes through source. observedThe pause button can only ever switch things off. Granting new powers always requires the full reviewed publish path.
  11. I11 — Mutations. Every management mutation requires the bearer plus an Idempotency-Key bound to method, path, and body; unknown JSON keys are rejected; key reuse with different input fails. observedRetrying a flaky request is always safe — it can never accidentally do the thing twice or do a different thing.
  12. I12 — Handles. Handles are unique platform-wide and never released; at most one rename per Account, ever; a retired handle resolves to the same Account (MCP: 200 in place; pages: 301). Minimum four characters; authority words (admin, support, official, …) reserved (PD 0004). changeA name you've seen for an Angel can never quietly come to mean someone else's Angel. Old links keep working and always point at the same owner.
  13. I13 — Preview isolation. Preview binds its own Connections; a preview publish with no preview bindings fails, naming the two ways forward; sharing production credentials is explicit and typed (PD 0005). changeA practice run can never silently touch your real data. If you want it to use the real accounts, you have to say so in so many words.
  14. I14 — Public surface. The public Angel page never touches the Broker, custody, or a key; no auth cookie is ever scoped to .angelmcp.ai (PD 0002). changeThe shareable page is pure reading material — nothing on it can reach anyone's credentials or session.

Priority rules — when X and Y conflict

  • P1 — Fail closed beats availability. Enforcement uncertainty (gate mismatch, custody failure, malformed provider result) refuses the call. Convergence failure is HTTP 500 / JSON-RPC −32603, and that status is intended.When in doubt, the system says no. A refused action is a nuisance; a wrongly allowed one is a betrayal.
  • P2 — Isolation beats convenience; convenience beats empty ceremony. Credential and environment isolation are never traded for fewer steps (PD 0005). But a step that protects nothing is a defect (PD 0003): first publish goes straight to live because there is nothing yet to protect.We remove steps that only exist to feel careful, and we keep every step that actually protects your data — even when it costs a second account setup.
  • P3 — Publish-time rejection beats runtime failure. What cannot execute must not deploy: unsupported operations fail at publish (registry), missing scopes fail at deploy (409), not at the provider. The one live exception is documented in the FAQ as a doc bug.You find out something won't work when you set it up — not later, when your agent is mid-task.
  • P4 — Document precedence. This spine wins over every other artifact here; ROADMAP.md owns sequence and status; the ADR/PD indexes' Status lines are authoritative over any individual record's prose (PD 0003 vs PD 0005 is the standing example).When two documents disagree, there is always one designated winner — nobody has to guess which page is current.

4 · Evals normative

Concrete inputs → expected outputs, in the style of the deterministic golden harness (runnable without credentials except where marked). Coverage: every goal G1–G6, the main error states, and every invariant except I14, with I11 (every management mutation carries a bearer token and an Idempotency-Key bound to method, path and body) only partly exercised, by E14's conflict case. I14 (nothing on a public, keyless path can reach the Broker, custody, or a key) has no eval yet because the public page it guards is unbuilt; it is the acceptance test to write alongside PD 0002. Where an eval specifies target-state behavior not yet built, it is the acceptance test for that work. Checkable stories: "if a user does this, exactly this happens." Each one protects a promise from the Spine. Plain-language version of each follows the technical one.

E1 · One command to live G3, I2, I9 · change

Given a fresh angels/inbox-read/ with valid ANGEL.yaml + angel.json and one healthy Connection. When angel publish inbox-read. Then: "created new Angel" is announced; both environment keys print exactly once; production answers tools/list at /@acme/inbox-read with the published digest in x-angel-policy-digest. Re-running publish with unchanged source returns the same Version and prints no keys.You write one short file and run one command — your Angel is live, with an address you can paste into any agent app. The key is shown once: copy it right then, it is never shown again. Run the same command twice and nothing duplicates.

E2 · Preview refuses to touch real data silently I13, P2 · change

Given angel.json with production bindings only. When angel publish --preview. Then: non-zero exit, nothing deployed, error names both remedies (bind preview / explicit share flag). When re-run with the explicit share flag, then preview deploys bound to production's Connections and the deployment record shows the sharing was requested.Preview never affects production data. Publishing with --preview will not use your production connections — you'll need to connect test accounts for preview mode, or explicitly override and share your production connections.

E3 · Exact promotion, stable keys G6, I2, I9 · observed

Given Version 2 previewed and deployment dep_A active. When promoting with {stagedDeploymentId:"dep_A", expectedDigest: d2, bindings}. Then production serves d2 byte-identically, the production key set is unchanged, and responses carry x-angel-version: 2. When expectedDigest is stale or dep_A is no longer active → 409, nothing changes.Say version 2 tested fine in preview: promoting ships exactly those tested bytes to production. Agents already connected don't miss a beat — same key, same address. If the preview changed under you in the meantime, the promotion is refused instead of guessing.

E4 · Two receipts or no result G6, I3 · observed

When an allowed tools/call executes, then _meta carries gateway and broker receipts agreeing on the identity fields, redacted per AgentSafeGateReceipt. When the gates' identities diverge (forced in the harness), then HTTP 500, -32603 "Angel gates failed to converge", and no provider call is made.When your agent reads an email, the response carries two independent receipts showing both checkpoints approved that exact call. If the checkpoints ever disagree, the read simply doesn't happen and the agent gets an error.

E5 · Guards bind arguments G1 · observed

Given the two guard shapes as they exist in the checked-in artifacts: gmail-inbox-zero forbids values (messages.modify and threads.modify, addLabelIds/removeLabelIds with forbiddenValues: [TRASH, SPAM, SENT]), and gmail-read-and-draft pins one (messages.list, maxResults pinned to "5"; google-read-proof carries the identical pin, and the call below exercises gmail-read-and-draft). Then: modify against gmail-inbox-zero with addLabelIds:["TRASH"] → 200, isError, denial.reason:"guard_denied", receipted; list against gmail-read-and-draft with maxResults: 50 → executes with effective maxResults: "5"; messages.send → unknown_tool against either (it does not exist in the artifact).Two ways an owner can bind what an agent may ask for. A forbidden value: the inbox Angel allows relabelling and archiving, so when an agent asks to move a message to Trash the call is refused and the reason is logged. A pinned value: the read-and-draft Angel fixes the result count at 5, so an agent asking for 50 gets 5. And "send" is in neither toolbox — there is nothing to refuse, because there is nothing to call.

E6 · Selection, never fan-out I7, I8 · observed

Given one tool bound to two Connections. Then: tools/list shows one tool with required angel_connection oneOf two arc_… refs titled by provider identity, never nicknames; omission → connection_required; a stale ref (from before a redeploy) → connection_unavailable; with exactly one Connection, omission selects it.If you've connected both personal and work Gmail, every call must say which one — the agent picks 'gmail — work account' from a menu. If it forgets, it's asked to choose. There is no 'both at once'.

E7 · Pause removes, resume restores I4, I10 · observed

When pausing one tool+Connection tuple, then that call → connection_paused while the tool's other Connection still serves; pausing the last active Connection drops the tool from tools/list; direct call → tool_paused. Pause all → resume one restores exactly that one. Availability changes install Broker-first per I4.Pause your work account on one tool and your personal account keeps working on it. Pause everything before a holiday, then resume just one tool — only that one comes back.

E8 · Isolation is invisibility I6 · observed

When any request names another Account's Angel, Version, Connection, or key — via /v1, the dashboard API, or MCP — then 404 with no existence signal. A staging/preview key presented to production → 401.Someone guessing at other people's Angel addresses gets 'not found' — the same answer a made-up address gets, so they can't even confirm an Angel exists. And a preview key never opens the production door.

E9 · Custody is write-only and loud I5, P1 · observed (credentialed acceptance)

Then: a stored Provider App reads back as safe summary only (no client secret, ever); revoking a Connection makes the next call fail loudly (−32003 family, Connection marked error); row-level Reauthorize restores the same Connection identity and calls pass again with deployment, keys, and Version unchanged. No fixture is ever substituted for a failed provider call.Once you save a Google credential you can never view it again — neither can we, through any API. Revoke access at Google and the call fails with a clear error instead of pretending; click Reauthorize and the same connection comes back, nothing to reconfigure.

E10 · Handles hold their meaning I12, G5 · change

Given acct_m1 handled @acme, renamed once to @acme2. Then: MCP at /@acme/google-read-proof → 200, same Account, no redirect; the page → 301 to @acme2/…; a second rename → refused; registering support (reserved) or abc (<4 chars) → rejected; no other Account can ever take acme.Say you rename @acme to @acme2. Every old link and every agent still configured with @acme keeps working and still reaches you — and nobody else can ever register @acme. You get exactly one rename, so choose carefully.

E11 · Delete is deliberate and total I4 · change

Given a live production deployment. Then: delete without typed slug → refused (409); with it → keys revoked first, gates reset Broker-then-Gateway, Angel gone from state, coordinate → 404, shared Connections and other Angels untouched, slug immediately reusable; delete when production is empty needs no confirmation; the same idempotency key replays safely.Deleting a live Angel makes you retype its name, so a pasted command can't do it by accident. Afterward agents get a clean 'not found', your other Angels and connections are untouched, and the name is immediately free — which is also how renaming works: publish under the new name, delete the old.

E12 · Publish-time closure I1, P3 · observed

Then: an operation the registry cannot derive fails at build/publish; an artifact whose digest, canonical source, or sealed templates disagree with the registry → 400 at publish; a deployment binding a Connection missing a required scope → 409 at deploy — before any runtime call. (The manual's "deploys, then fails at Google" sentence is wrong — see FAQ.)If your policy asks for something the platform can't actually run — or your Google account never granted the needed permission — you're told at setup with a specific message. You never find out from a mysterious failure days later.

E13 · Agent-only onboarding G4 · change · manual acceptance

Given an agent with only docs.angelmcp.ai — no repo, no prior context. Then it can walk a user from an empty directory to a promoted Angel the agent can call over MCP using the documented API/CLI path; llms.txt and SKILL.md resolve unauthenticated at stable URLs; docs state which steps need which credential. npm and (directionally) curl install paths are both documented.A user tells their AI assistant 'set up an Angel for me', and using only our public docs site it does the whole thing — no GitHub account, no cloning our code, no support ticket.

E14 · Transport error states P1, I11 · observed

Missing/wrong Angel key → 401 / −32001 before the body is read. GET on MCP → 405 + Allow: POST (until the public page exists at the coordinate — then GET renders it, POST still invokes). Wrong Accept → 406; wrong Content-Type → 415; foreign Origin → 403; missing MCP-Protocol-Version after initialize → 400. Same Idempotency-Key + different body → 409. Mutation during pending repair → 409 until the identical retry completes it.Wrong key, wrong method, wrong format — each mistake has its own specific answer, so you (or your agent) can instantly tell a typo from an outage from a permissions problem.

E15 · Gmail write under real guards G2 · change · M2 gate

Given a draft-and-read Angel (e.g. gmail.users.drafts.create allowed, messages.send absent) and a Connection whose grant covers the write scope (needs #10). Then: draft creation succeeds through both gates with receipts; messages.send → unknown_tool; guard-forbidden argument values on the write path → guard_denied; deterministic CI covers the transcript and a live credentialed acceptance proves the write.The flagship test: your own agent — the one you already use — drafts emails for your review through the Angel, and provably cannot send them. Seeing the draft appear in Gmail while knowing 'send' isn't in its toolbox is the whole product promise in one moment.

  • Reset fabricates Connections. POST /api/demo/reset seeds con_personal_google/con_work_google as healthy over real reconciled custody state.

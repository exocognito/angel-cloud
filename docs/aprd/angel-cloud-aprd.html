Angel APRD v2 — the complete end state

Angel's complete end state is one inspectable policy bundle that runs locally and in the cloud, with its proof and trust boundary visible from setup through every call.

This document maps the complete coherent end state of Angel across its three surfaces — www, CLI, and agent — and then, at the end, marks which subset ships first. The map never shrinks for scope; scope is chosen in §8. Colors everywhere grade reality, not decisions: a decided-but-unbuilt path is amber. All statuses were regenerated against main@faf4beb (2026-07-30), the commit this revision was written from.

0 · Terminology

This section states no product requirement. It defines the words every requirement, doc, interface, and claim must use. Where older copy disagrees, this section wins.

The rule that keeps breaking: an Angel is a toolbox, not an actor. The user's agent calls a tool through it. Never write that an Angel reads, drafts, sends, books, answers, or decides.
Term Precise meaning Use / avoid
Angel A policy-defined toolbox compiled into an immutable Version. It has no loop, session, or intent. Say “an Angel that allows drafting.” Never say “the Angel drafts.”
Agent The user's own MCP client. Angel Cloud does not supply, host, or replace it. Say “your agent calls the tool.” Never say “Angel Cloud's agent.”
Account The cloud tenant boundary. Every cloud Angel, Connection, and credential belongs to one Account. Local grant profiles belong to the local owner and device, not to a cloud Account. Do not substitute workspace, team, org, or user when the cloud tenant is meant.
Provider App / grant / Connection A Provider App is OAuth client material. A grant is provider authority from consent. A local grant profile stores that grant in the Angel-owned encrypted local vault. A cloud Connection stores it write-only in Broker custody. apps connect --local creates a local grant profile selected by grant nickname; --cloud creates an Account-owned Connection selected by Connection nickname in cloud bindings. Never call local custody a Connection.
Charter / policy The charter is review notes. The policy is the only authority the engine enforces (D3). Never imply that charter prose overrides, widens, or narrows the compiled policy.
Tool One canonical provider operation exposed over MCP. An absent operation is absent from tools/list. Say “the tool is not in the Angel.” Do not call it a permission or endpoint.
Gate / guard Gateway and Broker are independent gates. A guard is one argument rule inside a policy. They are not synonyms. Avoid “guardrails” as a catch-all.
Bundle / Version / engine The bundle is the reproducible trust object. Its Version is the immutable digest-addressed artifact. The engine interprets it. A Version never changes. The bundle pins the engine version in v2.
Production / preview The two cloud environments. A bare publish targets production; --preview opts into isolated practice bindings. Do not say staging, sandbox, or dev mode.
Receipt Hash-chained evidence of one gate decision. The agent sees the fields needed to use and anchor it, not private custody data. Do not use audit trail for a record that is not hash-chained.
Handle The Account's permanent public name in @handle/angel. Do not call it a username, slug, or vanity URL.

Document precedence. The Product Ledger owns the final goal, roadmap, learning disposition, and build approval. An approved APRD owns only its next-milestone build contract; this draft is not yet approved. The ADR/PD index Status line says whether a record governs; when a settled record and this page conflict, fix this page. 1 · Flagship statement DRAFT — wording awaits Sam's sign-off

"Angels do only what their charter allows — statically, provably, on every call."

The sentence is draft because “charter allows” is plain speech while the policy is the only authority (§0, D3). The intended claim is fidelity: the system does what the compiled policy says, and you can check. It is never a verdict that the policy is wise. No model, prompt, or judge sits above the policy, on any surface (D6 — ADR candidate).

Nature of the thing 3

Green

An Angel cannot act

No code path initiates a provider operation except an agent's authenticated tools/call. There is no scheduler, queue consumer, or mailbox: an Angel has no loop and no intent, so no sentence anywhere in the product may have one act.

code inspection — the three runtime Workers expose no timer or trigger; every Broker tool invocation carries a Gateway receipt born from an authenticated MCP call.

An Angel never starts anything by itself. Your agent starts each operation through the toolbox. We don't supply an assistant — you keep using the one you already have.

Green

Rules are compiled, never judged

The runtime stores and enforces compiled, digest-addressed artifacts, and no model or prompt sits anywhere in the decision path. Control may store an owner-only source draft for www editing; the pinned compiler runs in the browser, and only its canonical artifact crosses the publish boundary. No server runs a user's build (ADR 0006).

publish accepts only the built angel.version.json plus its digest; the gate evaluator is pure allowlist-and-guard logic (ADR 0005).

What your assistant is allowed to do is written in a short file you approve up front. No AI decides on the fly whether something seems okay — the engine follows fixed policy rules.

Green

One invocation surface, fixed service topology

MCP is the only invocation surface — REST invocation is reserved, unbuilt. Execution and control use three shared Workers, constant as Angels multiply; the future public apex route is another shared edge, never per-Angel infrastructure. The Broker has no route at all.

the three wrangler configs; the Broker's workers_dev is disabled with no public route declared.

Adding an Angel never means deploying another service. People can make several small toolboxes — one for email, one for documents — rather than one that can do everything.

Enforcement 4

Green

Absence, not refusal

tools/list returns exactly the deployed allowlist. An operation absent from the artifact answers unknown_tool — it is not blocked; it does not exist.

eval E5 in the golden harness — messages.send against a read-and-draft Angel is unknown_tool, not a denial.

If you didn't put "send email" in the toolbox, your assistant doesn't even see a send option. There is nothing to try — it just isn't there.

Green

Guards bind arguments

A forbiddenValues hit answers a receipted guard_denied; a pin overrides whatever was asked and executes at the pinned value.

the checked-in Angels — gmail-inbox-zero forbids TRASH/SPAM/SENT on relabel; gmail-read-and-draft pins maxResults to 5. Both run in bun run check.

You can allow an action but limit how it's used. One of our Angels lets an assistant tidy an inbox but never move anything to Trash. Another caps every search at five results — ask for fifty, you get five.

Green

Two receipts or nothing happens

Gateway and Broker evaluate every executed call independently; the response carries both hash-chained receipts, redacted for agents (AgentSafeGateReceipt). Forced divergence: HTTP 500 / −32603 and no provider call — that status is intended. Neither gate falls back to an older Version or availability state.

eval E4 — the harness forces the gates apart and asserts the refusal reaches the agent with no Google call made.

Two separate systems check every provider action before it executes, and both checks come back attached to the result. A first-gate denial stops there; if the two gates disagree, nothing happens. When in doubt, the answer is no.

Green

What can't execute doesn't deploy

An operation the registry cannot derive fails at publish. A binding whose Connection lacks a required scope fails at deploy with 409, naming the operation and the scopes that would cover it — never at the provider mid-task.

eval E12; bindingOperationGaps in the deploy path derives the per-operation scope floor from the adapter registry.

If something can't work — say your Google account never granted a permission it needs — you're told when you set it up, in plain words. Not days later, in the middle of a task.

Versions & release 3

Green

Byte-for-byte promotion

A Version is immutable and digest-addressed. Promotion installs the staged bytes exactly; a stale digest or inactive deployment answers 409 and changes nothing; republishing identical source returns the same Version and prints no keys.

evals E1/E3; every MCP response carries x-angel-version and x-angel-policy-digest.

Going live installs the exact version you tested — the same bytes, not a rebuild that might differ. Nothing changes behind your back.

Green

One command to live

angel publish takes source straight to a live production endpoint; --preview opts into the practice environment. Shipped in @smcllns/angel-core@0.3.0, published and pinned here.

the 0.3.0 README's contract; acceptance CI proves /@oscodev/google-read-proof answering live.

One command and your Angel is live, with a web address you can paste into any assistant app. If you want a practice copy first, you ask for one — it never happens by default.

Green

Preview never touches real data silently

Preview binds its own Connections. A preview publish with none is refused with 400 naming both remedies: bind preview Connections, or pass --share-production-credentials. Sharing real credentials is always said in words.

eval E2; deployPreview's server-side refusal; the typed share flag ships in 0.3.0.

A practice copy uses separate test accounts. If you haven't set any up, publishing stops and offers two choices: connect test accounts, or say explicitly that you want your real ones used. It never happens quietly.

Custody & isolation 5

Green

Credentials go in, never out

Provider credentials are write-only: envelope-encrypted per Account, leased only inside the Broker, never returned by any API. Only the Broker holds the KEK — and the Broker has no public hostname, ever. Custody failure throws; it never substitutes a fixture.

eval E9 (credentialed acceptance); Provider Apps read back as safe summaries with no client secret; the Broker declares no route.

When you connect a Google account, its credential goes into a vault nothing on the internet can reach. It can be used for allowed actions, but never read back out — not by your assistant, not by us, not by you.

Green

Other tenants don't exist

A request naming another Account's Angel, Version, Connection, or key answers 404, indistinguishable from nonexistent — on /v1, the dashboard API, and MCP alike. A preview key on production answers 401; an unknown handle answers 401 exactly like a wrong key.

eval E8, run across all three surfaces in the golden journey.

An outsider gets the same generic answer for your resource as for a made-up one: not found on management paths, or unauthorized at the keyed MCP door. They can't tell whether it exists.

Green

Nicknames never reach agents

Agents receive opaque deployment-scoped refs (arc_…) and provider-derived labels. Nicknames, Connection IDs, account IDs, and credentials appear on no agent-facing surface. Receipt argumentsDigest becomes agent-facing for local replay (D10); sequence, previousHash, and hash become agent-facing so the client can anchor and verify its chain tail (D11).

eval E6; the AgentSafeGateReceipt field list is the redaction contract.

Say you nickname a linked account "therapy inbox". Your assistant never sees that private nickname. It sees an opaque choice plus the identity label the provider supplied.

Green

Selection, never fan-out

A tool bound to several Connections requires the platform-reserved angel_connection selector; omission answers connection_required; exactly one bound Connection auto-selects. The compiler rejects policies declaring the selector; fan-out is inexpressible (ADR 0002).

eval E6 — one tool, two Connections, and the required oneOf the agent must choose from.

If you've connected both work and personal Gmail, every action has to say which one. If your assistant doesn't say, it's asked to choose. Acting on both at once isn't possible.

managementConnections() in src/workers/account-registry.ts:671, still called from the reset path at :415 — reverified at faf4beb.

Lifecycle 3

Green

Pause only removes

The availability overlay can only switch off — at environment, tool, or tool+Connection scope, most specific winning. Overrides survive promotion by following the stable connectionId (the incident-#1 fix). Changes install Broker-first; an interrupted change leaves a repair marker and conflicts with 409 until the identical retry completes it.

eval E7; the promote-overrides regression test added with PR #16.

You can pause one action, one account, or everything — and later resume exactly what you choose. A pause can only turn things off. Nothing ever gains a new ability from a toggle; new abilities go through the file you review.

Green

Delete is deliberate and total

Keys are revoked and persisted before teardown, Broker gates close first, receipts drop with the Angel, the coordinate answers 404, and the slug is immediately reusable — which is also how rename works. Typed-slug confirmation (missing → 409, wrong → 400) is required only while production holds a live or pending deployment. API and angel delete both shipped.

eval E11; DELETE /v1/accounts/:account/angels/:slug plus the 0.3.0 command.

To delete a live Angel you retype its name — no accidents. Then it's fully gone: assistants get "not found", nothing else of yours is touched, and the name is free to use again.

Green

Mutations are idempotent

Every strict /v1 mutation requires the management bearer plus an Idempotency-Key bound to method, path, and body. Dashboard actions authenticate the Access identity and derive their stable internal mutation key. Unknown JSON fields are rejected; the same key with different input answers 409; replays return the original response.

eval E14's conflict case; the golden journey runs strict mutations through the transport contract, while dashboard actions reach the same idempotent backend.

If a command fails halfway on bad wifi, run it again. A retry can never publish twice, delete the wrong thing, or quietly do something different from the first attempt.

Verification & the trust boundary 4 · new in v2

Four commitments added by the M2 trust review (D8, D10–D14). All four are committed, not built.

Orange

Anchored receipt tail

Every call response returns the receipt's sequence, previousHash, and hash; the client remembers the newest sequence and hash; the activity API serves fetch-by-sequence-range. For a fetched range, the first receipt's previousHash must equal the remembered hash and each later previousHash must equal the prior receipt's hash. Rewriting history must then fool a tail the platform no longer holds, and a gap in your own calls' sequence numbers bounds omission (D11). Today agentSafeGateReceipt (src/mcp.ts:212) strips all three chain fields.

a response whose receipts carry sequence + previousHash + hash; a range fetch whose first link extends the remembered tail and whose later links form one continuous chain.

Your assistant keeps a small stub from every receipt. If the record were ever rewritten, the stubs would stop matching — and a gap in the numbering would show that something was left out.

Orange

Engine pinned per angel

The bundle records the angel-core version it was built with; the cloud stamps it into receipts; publish hard-fails when the pin differs from the single hosted engine version. The engine version joins the seven-field receipt identity, making it eight — engine drift becomes visible where policy drift already is (D8, D12). True multi-version hosting is its own later milestone.

a publish refused for a mismatched pin; a receipt carrying the engine version; the identity cross-check (src/workers/gateway.ts:479) extended to eight fields.

The version of the rule-reading engine is written into your Angel and into every receipt. A quiet engine change can never silently change what your rules mean.

Orange

Behavior spot-checkable by replay

For calls its own agent made, the client holds the arguments and the v2 agent-facing receipt carries the cloud's argumentsDigest. Top-level angel replay <angel> --receipts <path> [--receipts <path> ...] --bundle <path> re-runs the same tool + arguments through the local engine over the same bundle and compares decision, detail, and the recomputed digest (D10). Today agentSafeGateReceipt strips argumentsDigest. Sampling, not proof — but evidence the platform cannot manufacture. Replay starts no server, opens no port, reads no credential store, writes no report file, and makes no network or provider call; every mismatch fails.

a replay run over recorded calls reporting decisions and argument digests all matching — or naming the first one that doesn't.

You can re-run any of your own calls at home and check that the cloud judged it exactly as your own copy of the rules would.

Orange

The trust boundary is stated, not implied

"Everything attestable is client-checkable; execution is trusted, bounded by replay." angel verify prints that sentence with its result; no surface implies a stronger claim (D13). Signed attestation is deferred and recorded as committed-later (D14).

the verify transcript in §4.6; a copy sweep finding no surface that claims remote execution is provable.

We tell you exactly where proof ends and trust begins, inside the tool itself — instead of letting you assume a guarantee no host can honestly make.

Evidence contracts · E1–E16

Commitment cards cite these stable ids. Each line is a concrete input → expected output contract; target-state lines become the acceptance test for their phase.

  1. E1 · One command to live. Given a fresh valid Angel and one healthy Connection, angel publish creates it, prints both environment keys once, and serves the published digest; an unchanged republish returns the same Version and no keys.
  2. E2 · Preview refuses real data silently. Given production bindings only, angel publish --preview exits non-zero and names both remedies; the explicit share flag deploys preview with a recorded production-Connection share.
  3. E3 · Exact promotion, stable keys. Promoting one active staged deployment with its expected digest installs those bytes and preserves production keys; a stale digest or inactive deployment returns 409 and changes nothing.
  4. E4 · Two receipts or no result. An allowed call returns agreeing Gateway and Broker receipts; forced identity divergence returns HTTP 500 / JSON-RPC −32603 and makes no provider call.
  5. E5 · Guards bind arguments. A forbidden label returns receipted guard_denied; a pinned result count executes at the pin; an absent send operation returns unknown_tool.
  6. E6 · Selection, never fan-out. Two bound Connections make angel_connection required with opaque refs; omission or a stale ref fails, while one available Connection may be selected implicitly.
  7. E7 · Pause removes, resume restores. Pausing one tool+Connection affects only that tuple; the last active Connection removes the tool from discovery; pause all then resume one restores only that one, Broker-first.
  8. E8 · Isolation is invisibility. Cross-Account management resources return the same 404 as absent ones; an unknown handle or wrong environment key returns the same 401 as a bad key.
  9. E9 · Custody is write-only and loud. Provider Apps read back as safe summaries; revoked custody makes the next call fail without a fixture; reauthorization restores the same Connection identity.
  10. E10 · Handles hold their meaning. A retired handle keeps reaching the same Account, a second rename fails, reserved short or authority names return 403, and no other Account can claim the old name; public pages later add the 301.
  11. E11 · Delete is deliberate and total. A live delete needs the exact slug; success revokes keys, resets Broker then Gateway, removes the coordinate, preserves shared Connections and other Angels, and replays idempotently.
  12. E12 · Publish-time closure. An operation the registry cannot derive or an artifact whose sealed content disagrees fails at build/publish; missing Connection scopes fail at deploy with the operation and covering scopes named.
  13. E13 · Agent-guided onboarding. An agent starting with the public docs can guide a person from an empty directory to a callable Angel, with each human credential step stated and every agent document available without login.
  14. E14 · Transport error states. Wrong key, method, content negotiation, content type, origin, protocol version, idempotency reuse, and mutation-during-repair each return their specified distinct error before unsafe work.
  15. E15 · Gmail write under real guards. A draft-and-read Angel creates a real Gmail draft through both gates with receipts, exposes no send operation, denies forbidden write arguments, and passes deterministic plus live credentialed acceptance.
  16. E16 · Public capability summary is private by construction. Generated low-entropy source and guards produce semantically identical HTML and JSON projections of one strict angel.public-review.v1 object with only the exact allowed keys; repeated reads of one Version keep one commitment, another Version gets another commitment, owner evidence can verify each commitment, unknown keys fail, every same-Version public surface withholds the raw digest, and the nonce, exact policy, identity, custody, and deployment data never appear.

4 · The stations, long form

One subsection per map row. Each states the end-state design, the decisions behind it (D-numbers from the 2026-07-30 register), and what exists at faf4beb. v1's journeys A–E fold in here.

4.1 · Get in

Identity is Better Auth self-hosted on the control worker, with Cloudflare D1 for auth storage and email delivery for the links (D18) — auth stays inside the same Cloudflare trust boundary as everything else. Sign-in is an email magic link that is single-use and expires exactly 600 seconds after server-side commit; a passkey is offered after the first sign-in, never required before it; recovery contacts never drop below one. Account deletion is an asynchronous, retryable hard-delete. It marks the Account deleting and removes authority first, revokes external grants before refresh-token destruction, physically deletes Account-owned angels, Versions, deployments, bindings, gates, receipts, keys/tokens, custody, Provider Apps/Connections, OAuth/idempotency/auth state, owner source, and public-review commitment nonces, then removes live handle mappings and finishes only after deletion proofs pass. Preserve only non-resolving tombstones for current and retired handles, with no Account identifier or live mapping. A transient failure leaves the Account disabled and retryable. Local source, bundles, evidence, vault state, saved keys, agent config, provider content, and OAuth client projects remain independent; bounded Cloudflare logs and PITR may outlive live deletion and must be disclosed. The CLI signs in with angel account login: a browser hop, then a token on the machine. The agent path is guided — reading llms.txt is enough to walk a user through sign-up, but the magic link lands in a human inbox, so the human stays in the loop.

Today: none of it. Entry is a Cloudflare Access owner invite, and the tenant is hardcoded (ACCOUNT_ID: "acct_m1", wrangler.control.jsonc:11). No signup, no logout, no delete. This station is amber — agreed and unbuilt — and blocks every organic dogfood today.

4.2 · Create

Three doors, one file. ANGEL.yaml holds the charter and the policy. The charter is notes; the policy is the only authority (D3) — and checking that they agree is a preflight in the authoring skill, run by the agent before build or publish, never by the engine. The owner reviews the complete source — charter plus the enforced tools: or angels: policy — before build. Any valid action in the provider's source spec may be allowed: the spec is the menu, the policy is the filter, and there is no curated action allowlist to maintain (D4).

  • CLI — writing the YAML by hand works today; angel create <slug> scaffolds it (agreed, unbuilt). angel delete, with typed-slug confirmation while production is live, shipped in 0.3.0.
  • www — angels:create → new:CharterEditor. The editor has the source schema's mutually exclusive direct-tools and child-Angels modes: create an Angel, add tools and guards, or compose sibling Angels — everything the CLI compiler accepts. Control stores the owner-only, secret-free source draft; the browser runs the pinned package-root compileHostedAngel compiler, resolving child source from the same Account, and sends only the canonical artifact and digest to publish (ADR 0006). A missing child draft blocks with an import-ANGEL.yaml prompt; source is never guessed from an artifact. Source never reaches either gate, and no server runs the build. Nothing of this source path exists yet.
  • agent — YAML from a sentence; the owner reviews the complete source diff, including every allowed tool, guard, or child Angel, before anything builds (agreed, unbuilt).

4.3 · Connect an App

Both tiers are first-class in v2 (D20). Own OAuth client, for developers: bring a client from your Google Cloud console, walk a written checklist with links (unwritten today), and consent. The connect flow exists and works — behind one known 500 on adding a personal Gmail account, the dogfood's first blocker, still open. Hosted "sign in with Google", for everyone else: one click against a platform-owned verified OAuth app — gated on Google verification, an external dependency; a manual beta list of ≤100 users bridges the wait. Consent scopes are a Provider App property (#10, shipped), and the deploy-time scope floor is derived per bound operation, so a missing grant fails at setup, never mid-task. On the agent surface, consent deliberately stays human: an agent can open the browser, but only the owner clicks through Google's screens.

4.4 · Run locally

angel serve is a slim in-process runtime (D7): it loads the same bundle the cloud runs, evaluates policy with the same engine, proxies provider calls with the user's own tokens, and answers as a real MCP endpoint on localhost. No Cloudflare emulation. Local provider grants come from explicit angel apps connect --local consent and live in the Angel-owned encrypted vault; cloud grants come from separate --cloud consent and Broker custody. Grants never cross custody, and the callback/client-type boundary remains open in C16. The local path is cloud-independent (D17). One bundle, both runtimes (D1). Replay is the separate one-shot angel replay command (D10), which reads private receipts and the bundle, starts no server, and fails on every mismatch.

One command, straight to production (PD 0003); --preview opts into the practice environment, which binds its own Connections (PD 0005). All of that shipped in core 0.3.0. 4.6 · Verify

angel verify is trust-blocking, not a nice-to-have (D2), and it takes the strong form (D13): fetch the production artifact bytes, hash them client-side, compare against the local build and the pinned engine version, print the result — and print the trust boundary with it. The digest is SHA-256 over the artifact's canonical bytes without a trailing newline, so a naive shasum of angel.version.json "verifies" a false mismatch. That footgun is the whole case for verify doing the hashing itself. 

$ angel verify gmail-inbox-zero
local build          a004a3a3e1b06092…6eecdc5a
production (hashed here from fetched bytes)
                     a004a3a3e1b06092…6eecdc5a
engine pin           0.3.0 = hosted 0.3.0
✓ match — production enforces your exact policy bytes
trust boundary: everything attestable is client-checkable;
execution is trusted, bounded by replay.

Digest equality settles "production's allow list = my local build" — per call and retroactively, because every receipt carries the digest. What verify cannot settle is whether the platform executed what it wrote down; that is trusted, bounded by replay (§4.4) and the anchored tail (§4.7). Signed attestation is committed-later (D14). The digest above is real: rebuilt from angels/gmail-inbox-zero at faf4beb while writing this revision.

4.8 · Edit policy

Both sides may edit (D16). The CLI edits ANGEL.yaml and republishes; www edits with full parity (D21) through the same compile-and-publish pipe; an agent proposes a complete source diff and the owner reviews both charter and enforced policy. There is no sync protocol: the published digest arbitrates, angel verify flags divergence between a local file and production, and reconciliation is manual. The standing rule from the overlay commitment applies on every surface: a toggle can only remove; adding a tool or loosening a guard goes through source, build, publish.

Today: CLI source edit → build → publish works end to end. The www allow/disallow toggle is not policy editing: renderConnectionToggle sends pause_tool / resume_tool and the Settings copy says it never edits or republishes the Version. The www PolicyEditor and agent diff flow are unbuilt.

4.9 · Pause

Pause is the owner's off switch, and only an off switch — environment, tool, or tool+Connection scope, most specific winning; overrides follow the stable connectionId across promotions; changes install Broker-first. All of that is live. What's missing is the control: one [slug]:MasterToggle in the angel heading replacing the buried Settings section. Pause is deliberately www-only: it is the human's red button, and durable authority reduction goes through source anyway.

4.10 · Rotate a key

Rotation is overlapping named keys (D19): mint a second key while the first stays valid, migrate agents at leisure, then revoke the old one. Lost plaintext: sign in, mint a replacement, migrate, revoke. The last active key can never be revoked. This path already works on www: Agent Keys has New key, Rotate, and Revoke; New → migrate → Revoke is the overlap-safe path, while the current Rotate action swaps atomically. The server stores the active key-hash set (gatewayKeyHashes, src/gate.ts:134–143), and the FAQ states the lost-key path. The CLI has no key command; angel keys new|revoke is the agreed, unbuilt counterpart.

6 · Non-goals and deliberately-not-verified

  • No oracle. Angel never issues a safety verdict; there is no judge above the policy. The only claim is fidelity to the compiled policy the charter describes — whether that is a wise policy is for the owner and their own LLM to judge from the charter, the spec, the allow list, and the bundle. Any copy implying a "this is secure" assessment mis-sells the product (D6 — ADR candidate).
  • No server-side build or code-execution engine. Control stores secret-free source drafts for their owner, but the pinned compiler runs in the browser. The publish and runtime boundaries accept only canonical artifacts; source never reaches Gateway or Broker (ADR 0006).
  • MCP is the only invocation surface. REST invocation stays reserved, unbuilt.
  • Omission never means fan-out (ADR 0002), the Broker never gets a hostname, and no per-Angel service deployment — shared services stay constant as Angels multiply; Durable Object state scopes each Angel.
  • Reversed from v1: "no authoring or publishing from the web UI" is gone. www is a full-parity write surface (D21). Do not cite v1's non-goal.
  • Deliberately not verified (D15), so they never sneak back in as requirements: byte-identity of the production server code (unverifiable from outside in principle; the policy artifact plus replay is the meaningful surface) · provider-side effects (what Google did with a forwarded request is Google's ledger) · availabilityDigest matching a local build (it is runtime state, correctly).
  • Deferred, on the record: signed attestation (D14, committed-later); hosting multiple engine versions (D8 is staged — v2 pins and refuses, multi-version hosting is its own milestone); sharing/catalog (J6, parked until the first hundred users); signup-at-scale, billing, quotas, teams (out of scope until the milestone gate passes).

8.1 · Normative CLI-first golden path contract

This is the executable v2.1 contract. The complete command owner is v2.1 CLI user guide; the proof owner is v2.1 generative eval specification. If implementation wants a different command shape, it changes those target-state docs and this APRD first.

Persona and start: persona: a developer's own agent helping a developer-owner; empty starting state: a new directory with no repository clone, no ANGEL.yaml, no angel.json, no Angel Cloud account session, no local token, no provider Connection, no Angel key, and no Gmail draft.

Public entry and install: public-doc-only entry point: https://docs.angelmcp.ai/llms.txt, which points to https://docs.angelmcp.ai/SKILL.md. v2.1 install path: BLOCKED by O1. No install command is normative until namespace control and the final package identity are proved against a built candidate. @angelmcp/cli is a recommendation only; registry absence does not prove control. The final package must install the bare angel command. The current user manual remains the shipped Milestone 1 manual; it must not present target v2.1 commands as shipped behavior before implementation.

Human-only handoffs: human-only handoffs: magic-link browser sign-in, Google Cloud OAuth-client setup, provider consent, and final Gmail draft review. The agent may open the browser and prepare forms, but only the owner authenticates, consents, and confirms the Gmail draft.

Local-only independence proof: In a separate blank directory where Angel Cloud is unavailable and no Account login exists, install the CLI, run angel create local-draft-proof --template gmail-draft-without-send, angel build local-draft-proof, angel apps connect google --local --nickname local-gmail --scopes gmail.compose --app local-google, and angel serve local-draft-proof --port 7423 --grant local-gmail. local MCP proof: angel serve local-draft-proof --port 7423 --grant local-gmail prints http://localhost:7423/mcp, the bundle digest, the engine pin, and the local vault grant label. Save the MCP transcript and prove that no login, Control call, cloud Connection, deployment, Angel key, cloud receipt, or Broker custody record exists.

Managed journey: Start again with a fresh identity and directory. Reuse reviewed source bytes only; do not reuse the local grant, local profile, prior Account state, or credentials.

  1. Sign in. Run angel account login --control https://api.angelmcp.ai --account <handle>. Human-only handoff: magic-link browser sign-in. The CLI stores an Account-scoped management token in an Angel-owned local profile, never an ambient OS keychain, and prints the Account handle without printing bearer tokens. Exact management-token storage, encryption, and unlock remain a WS2 contract gate; O2's provider-vault passphrase design does not settle them. The link is single-use and expires exactly 600 seconds after server-side commit.
  2. Create source. Run angel create gmail-draft-assistant --template gmail-draft-without-send. The command writes angels/gmail-draft-assistant/ANGEL.yaml with gmail.users.drafts.create allowed and no gmail.users.messages.send tool. source/policy approval boundary: owner approves ANGEL.yaml before build, serve, publish, verify, receipt pull, or replay. If the source contains an unknown operation, a charter/policy mismatch, forbidden angel_connection, or a write scope not named in policy, the CLI fails here or at build before network or provider work.
  3. Connect Gmail. Run angel apps connect google --cloud --nickname cloud-gmail --scopes gmail.compose --app cloud-google. Human-only handoffs: cloud OAuth-client setup, browser auth, and provider consent. Connect creates custody, not a project binding; it prints the exact reviewed binding edit. The cloud grant stays in Broker custody and this managed journey never reads or copies the local grant.
  4. Build. Run angel build gmail-draft-assistant. It emits build/angel.version.json, build/angel.version.sha256, and the bundle's pinned engine version. Build is offline and secret-free.
  5. Bind the managed grant. Apply the printed production binding edit to angels/gmail-draft-assistant/angel.json, then review the resulting cloud binding before publish. This step writes only the cloud nickname; it never copies the local grant.
  6. Publish to production. production-default publish: angel publish gmail-draft-assistant. It builds, ensures the Angel, resolves production bindings, publishes the immutable Version, deploys it to production, prints the produced bundle path, digest, engine pin, production MCP endpoint, and first-time preview and production Angel keys. no-op replay: the unchanged publish returns the same Version and digest and prints no new keys. Preview remains opt-in with --preview; production is the bare default.
  7. Verify production. verify: angel verify gmail-draft-assistant --production. It fetches production artifact bytes, hashes them locally, compares them to the local build digest and engine pin, prints the production endpoint, and prints trust boundary: everything attestable is client-checkable; execution is trusted, bounded by replay.
  8. Call from an agent. agent call: tools/list, then tools/call gmail.users.drafts.create against POST https://mcp.angelmcp.ai/@<handle>/gmail-draft-without-send with the production Angel key. A successful draft call returns provider data and two receipts: Gateway and Broker. anchored tail: sequence, previousHash, hash appear in each agent-facing receipt, plus the digest fields needed for replay. A send attempt returns unknown_tool, not a denial.
  9. Pull receipts and replay. Pull an anchored range with angel receipts pull gmail-draft-assistant --production --gate gateway --from 128 --to 151 --anchor 127:<gateway-hash> --out receipts/gateway-128-151.ndjson and angel receipts pull gmail-draft-assistant --production --gate broker --from 93 --to 108 --anchor 92:<broker-hash> --out receipts/broker-93-108.ndjson, then run replay spot-check with angel replay gmail-draft-assistant --receipts receipts/gateway-128-151.ndjson --receipts receipts/broker-93-108.ndjson --bundle build/angel.version.json. The local engine recomputes decisions and argument digests for sampled calls and names the first mismatch.
  10. Stop before unsafe work. failure boundaries: every unsafe step fails before provider work. Unknown tools fail at build or tools/list; missing scopes fail at connect or publish; digest or engine mismatch fails at publish or verify; gate divergence returns HTTP 500 / JSON-RPC -32603 with no provider call; idempotency-key reuse with different input returns 409 before mutation; wrong key, bad method, bad content negotiation, bad content type, bad protocol version, and bad Origin fail before a gate or provider call.
  11. Acceptance. Human-only handoff: final Gmail draft review. done: Gmail contains a draft and no sent message. The done proof is a transcript showing the public-doc entry, install, the separate local-only transcript and MCP endpoint, the managed-journey production MCP endpoint, bundle path, digest, engine pin, first-time keys, verify trust boundary, two receipts with anchored tail fields, receipt pull, replay spot-check result, unknown_tool for send, the human-confirmed draft-without-send result, and generated E2E evidence from the six eval families.
